# Weather Ensemble App — Reference & Debug Guide

## Architecture

```
EventBridge (cron 0,12 UTC)
  → jtamerius-weather-collector Lambda (Python 3.12)
      ├── fetch tasks: GFS/ECMWF/ICON/GEM/HRRR det+ens → s3://jtamerius/partial/{run_id}/*.json
      └── assemble task (cron +20 min): merges partials
            ├── s3://jtamerius/forecasts/{lat}_{lon}/{run_id}.json  (per-location)
            ├── s3://jtamerius/grid_summary/{run_id}.json
            ├── s3://jtamerius/locations/manifest.json
            └── s3://jtamerius/weather/index.html                  (regenerated each run)

CloudFront E15B1H9LICVP1J (d326hhew368icp.cloudfront.net → jtamerius S3 bucket)
  → serves /forecasts/, /grid_summary/, /locations/, /weather/
  → CORS: Managed-CORS-With-Preflight on /forecasts/* + default behavior

Amplify d19cuiv0dybz8y (weather.jtamerius.com)
  → apps/weather-app/ React app (native react-plotly.js, no iframe)
  → fetches manifest + forecast JSON directly from d326hhew368icp.cloudfront.net
```

**CRITICAL DNS NOTE:** `jtamerius.com` (bare) and `www.jtamerius.com` both → Amplify landing page (returns 404 for data).
Data is ONLY served from CloudFront `d326hhew368icp.cloudfront.net`. The Lambda's `CDN_DOMAIN` env var MUST be that CloudFront default domain (not a custom domain — www was moved to the landing page).

## S3 Data Layout

```
s3://jtamerius/
  partial/{run_id}/           run_id format: 2026-04-21T12 or 2026-04-21T00
    gfs_seamless_det.json
    gfs_seamless_ens.json
    ecmwf_ifs025_det.json
    ... (one file per model/type)
  forecasts/{lat}_{lon}/      lat/lon to 4 decimal places, e.g. 37.2753_-107.8801
    {run_id}.json             assembled forecast for that location
  grid_summary/
    {run_id}.json             42-point grid summary
  locations/
    manifest.json             list of all 42 locations
  weather/
    index.html                app HTML, regenerated by Lambda each run
```

**App lookback window:** 10 days. If newest file in `forecasts/{loc}/` is older than 10 days, the app shows "No S3 data… Run Lambda first."

## Lambda CFn Stack Parameters

```
FunctionName         = weather-collector
ScheduleExpression   = cron(0 0,12 * * ? *)
DomainName           = www.jtamerius.com   ← MUST be www., not bare domain
WebsiteBucketName    = jtamerius
LambdaCodeBucket     = jtamerius-website-deploy
LambdaCodeKey        = lambda_package.zip
LambdaMemory         = 2048  (assemble task uses ~904 MB — MUST be 2048, not 512)
LambdaTimeout        = 600
MaxWorkers           = 10
BatchSize            = 100
```

The `DomainName` parameter flows into the Lambda env var `CDN_DOMAIN`, which the assemble task embeds as `DATA_ORIGIN` in the generated `index.html`. **If this is wrong, the app fetches data from the wrong URL and shows "No S3 data".**

## Diagnosing "No S3 data" Error

### 1. Check most recent data in S3
```bash
aws s3 ls s3://jtamerius/forecasts/37.2753_-107.8801/ --profile jtam --region us-east-1 | tail -5
```
Most recent file should be dated today or yesterday. If oldest file is >10 days ago, the pipeline is broken.

### 2. Check Lambda ran recently
```bash
aws logs describe-log-streams \
  --log-group-name /aws/lambda/jtamerius-weather-collector \
  --profile jtam --region us-east-1 \
  --order-by LastEventTime --descending --max-items 5 \
  --query 'logStreams[*].[logStreamName,lastEventTimestamp]' \
  --output table
```

### 3. Read latest Lambda log
```bash
# Get the most recent stream name from step 2, then:
aws logs get-log-events \
  --log-group-name /aws/lambda/jtamerius-weather-collector \
  --log-stream-name '2026/04/21/[$LATEST]<stream-id>' \
  --profile jtam --region us-east-1 \
  --query 'events[*].message' --output text
```

### 4. Check DATA_ORIGIN in live index.html
```bash
aws s3 cp s3://jtamerius/weather/index.html /tmp/w.html --profile jtam && grep DATA_ORIGIN /tmp/w.html
# Should show: var DATA_ORIGIN  = "https://www.jtamerius.com";
```

### 5. Test data URL directly
```bash
curl -sI "https://www.jtamerius.com/forecasts/37.2753_-107.8801/$(date -u +%Y-%m-%d)T12.json"
# Should return HTTP/2 200
```

### 6. Check CDN_DOMAIN env var on Lambda
```bash
aws lambda get-function-configuration \
  --function-name jtamerius-weather-collector \
  --profile jtam --region us-east-1 \
  --query 'Environment.Variables' --output json
```

## Common Fixes

### Fix: CDN_DOMAIN is wrong

The correct value is the CloudFront default domain `d326hhew368icp.cloudfront.net` — NOT `www.jtamerius.com` (www now points to the landing page).

Update Lambda env var:
```bash
aws lambda update-function-configuration \
  --function-name jtamerius-weather-collector \
  --environment "Variables={S3_BUCKET=jtamerius,MAX_WORKERS=10,BATCH_SIZE=100,CDN_DOMAIN=d326hhew368icp.cloudfront.net}" \
  --profile jtam --region us-east-1
```

Update the `DomainName` parameter in [template.yaml](apps/weather_app/ensemble-plumes/infrastructure/weather-collector/template.yaml) and the GHA workflow override so it persists across deploys.

Then trigger regeneration of index.html (see below).

### Fix: Trigger manual re-run of assemble step

**Always include `{"task":"assemble"}` payload.** The Lambda handler defaults to assemble when
no `task` key is present, so a bare invocation (e.g. console test event `{}`) silently runs the
assembler with whatever partials exist at that moment — even mid-pipeline. This has caused
premature assembly (missing ens models → dotted lines) during debugging sessions. Always
specify the task explicitly.

```bash
aws lambda invoke \
  --function-name jtamerius-weather-collector \
  --payload '{"task":"assemble"}' \
  --cli-binary-format raw-in-base64-out \
  --profile jtam --region us-east-1 \
  /tmp/assemble_out.json && cat /tmp/assemble_out.json
```
Response will show `ok/skipped/errors` counts. "skipped" means that run_id was already assembled.
If all are skipped, delete the stale forecast JSONs first (see below), then re-invoke.

### Fix: Re-assemble when all locations are skipped (assembler already ran prematurely)

The assembler skips locations whose forecast JSON already exists for the current run_id.
If a premature assembler run (e.g. triggered manually mid-pipeline) published bad forecasts,
delete the stale JSONs first, then re-invoke:

```bash
RUN_ID="2026-04-26T00"   # replace with current run_id (YYYY-MM-DDTHH format, HH = 00 or 12)
aws s3 ls s3://jtamerius/forecasts/ --recursive --profile jtam | grep "$RUN_ID" \
  | awk '{print $4}' | while read key; do
    aws s3 rm "s3://jtamerius/$key" --profile jtam
  done
# Then invoke the assembler (see above) and invalidate CloudFront
aws cloudfront create-invalidation \
  --distribution-id E15B1H9LICVP1J \
  --paths "/weather/index.html" "/forecasts/*" \
  --profile jtam --no-cli-pager
```

### Fix: Pipeline stopped — trigger full fetch + assemble for current run
The fetch tasks run in sequence 0–18 min past the hour; assemble runs at +30 min.
To re-run everything manually, invoke each fetch rule's payload in order, then invoke assemble.
Or wait for the next scheduled run (next 00:00 or 12:00 UTC).

## Lambda Source Code

The Lambda package (`lambda_package.zip`) is deployed from `s3://jtamerius-website-deploy/lambda_package.zip`.

The Lambda source is **not in this monorepo** — it was formerly a git submodule at `apps/weather_app/ensemble-plumes/` (removed in commit `25a0371`). To update the Lambda code, build and upload a new zip to that S3 key, then update the function:
```bash
aws lambda update-function-code \
  --function-name jtamerius-weather-collector \
  --s3-bucket jtamerius-website-deploy \
  --s3-key lambda_package.zip \
  --profile jtam --region us-east-1
```
